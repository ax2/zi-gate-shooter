## 1. 模块职责与数据归属

以下为职责划分；具体实现位于src/core、src/game、src/ui及微信入口。保持纯规则与表现分离，不引入复杂ECS框架或服务后端。

| 模块 | 唯一负责的状态/输入输出 | 关键边界与验收 |
|---|---|---|
| Session/Clock | runId、游戏状态、固定步、暂停/恢复/重开 | 唯一模拟时钟；失焦自动暂停、需手动恢复；无补发 |
| Input/Viewport | 拖动/键盘→逻辑坐标与移动意图 | 不瞬移、不越界；适配不改规则 |
| Combat | 发射快照、弹丸、连续碰撞、生命与死亡事件 | 最近目标，单弹一次；伤害不由特效回调发起 |
| Reward/Progression | 箱/门/掉落状态、row锁、阶级/加成/超载 | 统一事务提交；(runId,id,generation)去重 |
| Director/Reachability | 模板、种子、轮次、危险时间表和合法路径 | 安全回退；不追着玩家DPS改HP |
| Enemy/Boss | 3普通+精英行为，首领状态机 | 攻击预告有可达安全路；胜利只推进一次 |
| Presentation | 场景、实体动画、特效、声音、镜头 | 消费只读事件；不改变碰撞、奖励和计时 |
| HUD/Flow/Storage | 开始、设置、暂停、结果、本地最高分 | 只保存带版本的设置/最高分；损坏存储回默认 |
| Config/Diagnostics | 数值、波次、效果预算、调试采样 | 单位明确、启动时校验；本地调试默认关，无上传 |

依赖方向：输入→模拟步→碰撞/事件排序→奖励与战斗状态提交→导演器调度→表现与HUD。配置为只读输入。表现层不反向修改规则；每次重开由Session销毁或清空所有本局资源，再创建新runId。

统一事件至少携带 runId、实体代次、模拟时间、类型、有效伤害或奖励、目标ID。掉落与门结算保留本局最小去重集合，已不可能再到达的事件及时清理；不能为了去重无限保留所有历史子弹ID。

## 2. 时间、预算与稳健性设计

拟定固定步1/60s；同一模拟时长在不同渲染帧率下得出相同规则结果。渲染延迟使用累积器，最多单帧5步；长卡顿超过可恢复预算时显式自动暂停并提示继续，不跳过危险、不一口气补发大量攻击。失焦直接暂停；用户恢复时丢弃墙钟间隔。慢设备墙钟耗时与模拟时间须分别记录，不能用慢模拟假装60帧。

候选活跃对象上限：我方弹80、敌方弹48、普通敌人24、精英1、首领1、箱/门实体合计6、掉落2。T3最多24弹/秒×1.2秒≈29个在途弹，80留余量；超载只变伤害不增加碰撞弹。临界情况下先限制后续生成并清理出界对象；活跃奖励不能因为池满被复用。任何逻辑池溢出记为验证失败，不能悄悄丢子弹改变DPS。表现池可按美术规格降级。

最高分/设置本地存储失败时转内存状态，不阻止游玩；不保存未结束局进度。无登录、后台、云存档或遥测。文件资源缺失需明确错误或标记降级，不能以占位资源冒充正式版本。
