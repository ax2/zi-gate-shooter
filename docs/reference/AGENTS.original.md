# 项目交接规则

这是竖屏无尽数字门射击游戏。先读 `docs/GAME_DESIGN_HANDOFF.md`，并遵守仓库已有的有效说明。将本文用于已有项目时应合并，不直接覆盖原有指令。

## 固定需求

- 竖屏、角色位于底部、目标从上向下推进、击杀得分、无尽模式。
- 主要成长机制是持续射击装备箱或数字门，再取得奖励；不要改成仅打怪掉装备的传统纵版射击。
- 元素少，画面精细、爆裂、刺激；玩法清晰和高质量视觉同样重要。
- 用户未指定平台、技术栈、角色形象或具体参考游戏。文档中的默认项是建议，不是批准结果。

## 当前阶段

当前是策划交接，没有已完成的代码、原型、正式素材、批准的概念图或性能测试。新会话先完善规划；只有用户明确要求开始开发后，再进入实施。

不要重复询问已确定的核心需求。未确定的小项先做明确标注的合理假设；把需要用户决策的关键事项集中说明。

## 实施约束

- 修改前检查仓库、依赖、已有文件与工作区状态，不覆盖用户未提交的改动。
- 默认方案为 TypeScript + Vite + Phaser 浏览器原型。已有工程优先；版本需核查兼容性并锁定。
- 不擅自添加登录、后端、支付、广告、多人联机或基地经营。
- 正式视觉采用统一、清晰、可分层的素材。占位图形只能用于标明的机制验证，不冒充成品。
- 装备箱破碎后才掉落，拾取后才升级；数字门按有效伤害提高奖励，穿过后单次结算。
- 同排互斥数字门最多领取一次。伤害、奖励、事件监听和对象复用都必须防重复。
- 火力升级需改变外观、弹道或声音；不得立即按玩家实际输出同比增加敌人生命来抵消成长。
- 所有数值集中配置；模拟时间与渲染解耦；暂停、失焦、恢复和重开必须完整处理。
- 保留敌方攻击、门数字、箱子耐久和可通行路线；提供弱特效与震动关闭选项。
- 项目名称、素材、音频与界面自行设计，不直接搬用参考游戏资产。

## 验证和报告

运行仓库实际存在的类型检查、测试和构建。缺少命令时先检查或建立必要脚本，不能声称执行了不存在的测试。

按策划文档第 14 节验证核心规则；实际运行并检查手机尺寸、强火力状态和重开；视觉验收使用真实运行截图或录屏。

每次交付说明：实际变更、运行方式、通过的检查、失败与未执行项、尚存限制。没有真机数据就不宣称真机稳定 60 帧；没有批准概念稿就不宣称已按批准稿复刻。

持续记录重要决策到 `docs/DESIGN_DECISIONS.md`，实施阶段记录到 `docs/IMPLEMENTATION_PLAN.md` 和 `docs/TEST_REPORT.md`。
